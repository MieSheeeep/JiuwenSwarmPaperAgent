## 第 3 页：系统的总体工作流设计

### 【页面视觉呈现】
- **六阶段端到端流水线流程拓扑**：
  ```
  [Literature 文献检索] ──> 收敛对比策略与研究范围，形成领域上下文
          │
  [Plan 实验规划]       ──> 签署事前验收协议，形式化锁定对比指标与极性
          │
  [Pilot 小样本探针]    ──> 10%~20% 样本试探，引入弱基线实施三态剪枝早停
          │
  [Experiment 受控实验] ──> 调用 openJiuwen ReActAgent 真实跑批，沉淀审计账单
          │
  [Writing 论文编撰]    ──> 提炼证据统计表，Prompt 注入真实数据，LaTeX 编译 PDF
          │
  [Review 外部送审]     ──> 提交 Stanford Agentic Reviewer，获取客观第三方盲审反馈
  ```
- **核心工程原则**：
  - **角色解耦**：调度、执行、提取、编译各司其职，避免单一 Agent 上下文污染；
  - **证据严格绑定**：论文中所有图表与指标，均直接映射到原始 JSONL 实验账本；
  - **契约化状态流转**：阶段间通过不可篡改的数据档案传递，禁止凭空跳步。

### 【建议用时】
50 秒

### 【逐字答辩讲稿】
> 这是我们系统的总体工作流设计图。我们基于 openJiuwen Swarm 框架，将整个科研周期抽象为六个紧密衔接的阶段。
> 
> 整个流水线从**文献阶段**界定研究问题开始；进入**规划阶段**后，系统显式签署包含主指标和阈值的事前验收契约；在启动耗时耗资的大实验前，先通过**小样本探针阶段**检验可行性，实行剪枝拦截；一旦探针通过，即在**实验阶段**调度 openJiuwen 的 `ReActAgent` 与大模型 API 跑完预设实验，并将输入、输出与 Token 消耗持久化落盘；随后，**写作阶段**严格依据落盘的证据数据，利用大模型草拟英文正文，并调用标准 LaTeX 编译器生成双栏 PDF；最后在**评审阶段**，将论文提交至外部盲审网站进行客观打分。
> 
> 相比传统简单的串行 Prompt 调用，我们系统最核心的工程原则是**“证据严格绑定”**与**“契约式状态流转”**：下游写作模块引用的每一个准确率百分比和 Token 消耗数值，都必须溯源到底层原始实验日志，坚决斩断大模型在学术论文上的文字幻觉。

## 第 4 页：核心实验研究：智能体长配置历史的上下文选择机制

### 【页面视觉呈现】
- **研究背景与痛点**：
  - 智能体在多轮系统配置与长程任务中，上下文迅速膨胀；
  - **两难困境**：全量送入导致 Token 开销暴涨与注意力稀释，截取滑动窗口又必然丢失早期核心约束与依赖。
- **评测对比的 4 种上下文选择策略**：
  1. **All History（全量历史）**：将交互全周期的全部配置与交互记录完整喂入模型；
  2. **Recent Window（最近固定窗口）**：仅截取最近几轮的上下文（常规简易做法）；
  3. **Lexical Retrieval（基于项目检索）**：根据当前任务的 Project ID 及配置键进行词法抽取；
  4. **Retrieval + Summary（检索加摘要）**：检索关键历史的同时，对非核心历史做压缩摘要。
- **评测基准规模**：
  - 构建 24 个具备明确事实真值（Ground Truth）的多轮配置合成任务；
  - 任务涵盖多属性冲突覆盖、长程依赖调用、跨项目参数继承等复杂场景；
  - 4 种策略分别测试作答，总计运行 **96 次任务作答**。

### 【建议用时】
45 秒

### 【逐字答辩讲稿】
> 在核心实验课题的选择上，我们没有做空中楼阁式的选题，而是选取了一个直接关乎多智能体系统自身性能的核心工程课题——**“长配置历史下的上下文选择机制研究”**。
> 
> 当智能体面对长周期的运维或参数配置任务时，会面临一个典型的两难问题：把所有历史全部喂入模型，Token 消耗巨大且容易注意力分散；如果只截取最近几个窗口，又极易丢失早期的全局关键配置。
> 
> 为此，我们设计了 4 种具备代表性的对比策略：全量历史、最近滑动窗口、基于项目标识的词法检索，以及检索与摘要压缩混合策略。
> 
> 实验构建了 24 个具有明确事实标准的结构化评测任务，涵盖跨轮次修改、参数继承和多任务干扰。针对 4 种策略分别运行测试，累计执行了 96 次任务作答，完整记录不同策略的答题准确率与上下文开销。

### 【换页过渡语】
> “这 96 次作答的具体运行数据如何？消耗了多少 Token？请看第 5 页的真实实验审计报表。”

## 第 5 页：真实实验运行数据与 Token 资源消耗审计

### 【页面视觉呈现】
- **全生命周期 API 消耗审计报表（模型：deepseek-flash / 官方 DeepSeek API）**：
  | 运行阶段 | API 真实调用 | 输入 Token | 输出 Token | 总计 Token | 命中缓存 Token | 实际计算耗时 |
  | :--- | :---: | :---: | :---: | :---: | :---: | :---: |
  | **冒烟验证 (Smoke)** | 5 次 | 4,151 | 90 | 4,241 | 0 | 约 3.1 秒 |
  | **主对比实验 (Baseline)** | 120 次 | 99,644 | 2,124 | 101,768 | 3,328 | 43.8 秒 |
  | **二次验证 (Verified)** | 5 次 | 4,151 | 85 | 4,236 | 3,328 | 约 3.0 秒 |
  | **学术论文草拟 (Paper)** | 1 次 | 2,777 | 1,275 | 4,052 | 0 | 约 5.2 秒 |
  | **全流程累计** | **131 次** | **110,723** | **3,574** | **114,297** | **6,656** | **约 55.1 秒** |
- **核心实验数据结论**：
  - **准确率表现**：全量历史 (100%)、检索 (100%)、检索+摘要 (100%)，而**最近滑动窗口断崖式跌落至 25%**；
  - **根因分析**：由于关键配置项被故意置于第 1~3 轮，而滑动窗口仅保留末尾配置，发生了严重的灾难性遗忘；
  - **经济性表现**：检索策略在维持 100% 准确率的同时，大幅降低了每轮输入的 Token 峰值，兼顾了效果与成本。

### 【建议用时】
50 秒
