## 第 3 页：系统的总体工作流设计

### 【页面视觉呈现】
- **六阶段端到端流水线流程图**：
  ```
  1. Literature (文献收集)    ──> 整理相关工作，界定对比策略
         │
  2. Plan (方案设计)          ──> 确定实验参数、比较基线与衡量指标
         │
  3. Pilot (小样本探针)       ──> 抽取少量样本初测，设置早停检查
         │
  4. Experiment (受控实验)    ──> 调用 openJiuwen ReActAgent 跑实验并记录真实日志
         │
  5. Writing (论文编撰)       ──> 提取证据数据，调用 LLM 撰写正文并套用 LaTeX 模板
         │
  6. Review (外部送审与评估)  ──> 提交至 Stanford Agentic Reviewer 获取真实第三方打分
  ```
- **核心工程特征**：
  - 角色分工：调度、实验、写作各司其职；
  - 证据绑定：论文所有数字必须来自实验日志，严禁凭空捏造；
  - 源码无侵入：不破坏用户本地 openJiuwen 的原有配置。

### 【逐字汇报讲稿】
> 针对赛题目标，我们设计了包含六个标准阶段的系统工作流。
> 
> 首先由文献阶段收敛研究问题；规划阶段负责定义实验变量与评估指标；小样本探针阶段用于初步检验算法可行性；实验阶段实际调用 openJiuwen 的 `ReActAgent` 与大模型 API 跑完预设任务，并将输入输出和 Token 账单完整落盘；写作阶段依据真实的实验统计表，利用大模型草拟英文正文，并填入标准的 LaTeX 模板编译成 PDF；最后在评审阶段，将生成的 PDF 论文提交至外部盲审网站进行评测。
> 
> 整个流程最大的工程原则是**“证据严格绑定”**：写作模块引用的每一个准确率和 Token 数字，都必须能在实验生成的原始日志中找到对应的记录，彻底杜绝数据捏造。

## 第 4 页：核心实验研究：智能体长配置历史的上下文选择机制

### 【页面视觉呈现】
- **研究课题**：Agent 在面对长周期历史配置时，如何选择上下文以兼顾回答准确率与 Token 消耗？
- **对比的 4 种上下文选择策略**：
  1. **All History（全量历史）**：将所有历史配置信息全部送入上下文；
  2. **Recent Window（最近窗口）**：仅截取最近固定的对话轮次；
  3. **Lexical Retrieval（按项目检索）**：基于项目编号与关键词提取历史记录；
  4. **Retrieval + Summary（检索加摘要）**：检索关键历史的同时，对非核心历史做摘要压缩。
- **实验设计规模**：
  - 构造 24 个确定性的合成评测任务，包含修改历史、多配置项及依赖干扰；
  - 针对 4 种策略分别测试作答，总计运行 96 次任务作答。

### 【逐字汇报讲稿】
> 在具体的研究课题上，我们选择了一个与 Agent 系统自身息息相关的实际问题——**“长配置历史下的上下文选择机制研究”**。
> 
> 当智能体与用户进行多轮配置交互时，历史上下文会迅速膨胀。我们设计了 4 组对照策略：全量历史、最近滑动窗口、基于项目 ID 的关键词检索，以及检索加摘要压缩。
> 
> 我们构建了包含 24 个具有明确事实标准的测试任务，针对这 4 种策略分别运行测试，总计完成了 96 次任务回答，记录不同策略在回答准确率和 Token 消耗上的实际表现。

### 【页面视觉呈现】

  | 运行阶段 | API 调用次数 | 输入 Token | 输出 Token | 总计 Token | 缓存 Token | 运行耗时 |

  | **冒烟验证 (Smoke)** | 5 次 | 4,151 | 90 | 4,241 | 0 | 约 3 秒 |

  - 在当前合成任务下，全量历史、检索、检索加摘要均取得了 100% 的准确率，而最近滑动窗口由于丢失了早期依赖，准确率骤降至 25%；
  - 检索策略相比全量历史节约了大量的上下文输入开销。

### 【逐字汇报讲稿】
> 屏幕上展示的是我们系统主实验的真实资源账单。我们严格按照赛题的资源审计要求，记录了每一次调用的输入输出。
> 
> 实验采用官方 DeepSeek API，主实验共执行了 120 次真实 API 调用，消耗 101,768 个 Token，纯计算耗时为 43.8 秒；加上前置冒烟与最终论文撰写，全流程共调用 API 131 次，累计消耗 114,297 Token。

> 实验结果表明：在带有明确项目标识的测试集上，关键词检索与检索加摘要均保持了 100% 的准确率，而固定长度的滑动窗口由于遗漏了早期配置，准确率仅有 25%。这些真实的数据和图表，构成了后续撰写论文的全部事实依据。

  ```

                   │
                   ▼
  ```

## 第 8 页：外部评审暴露的真实问题复盘

### 【页面视觉呈现】
- **传统科研 Agent 生成论文的“虚胖”现象**：
  - **看似完整，实则单薄**：格式上具备了 Abstract 到 Conclusion，但实验缺乏深度；
  - **基线选择具有利己倾向**：只和最弱的固定窗口对比，没有对比工业界常用的真实基准；
  - **算力控制缺乏预警**：即便方向本身过于简单，Agent 也会盲目跑完所有调用。
- **评委/老师关注的核心本质**：
  - 外部网站给出的 4.4 分，实质上给所有科研 Agent 泼了一盆冷水：单纯靠“大模型写文字 + 套 LaTeX 模板”，是拿不到高水平科研成果的。
- **我们的思考与行动**：
  - 必须在 Agent 工作流中增加**硬性的约束与门禁**，不能让 Agent 盲目自嗨。

### 【逐字汇报讲稿】
> 拿到外部评审这 4.4 分后，我们团队进行了认真的复盘。
> 
> 坦白讲，这暴露出当前许多科研 Agent 的共同通病：看起来有模有样，但实质内容偏单薄。系统很容易挑选有利于自己的弱基线（比如简单的滑动窗口）做对比，得出貌似显著的结论，但一旦放到严格的同行评审尺度下，就会被一眼看穿。
> 
> 针对外部评审指出的这些真实痛点，我们随后在代码层面重点补齐了三项机制：第一是事前设定验收契约，第二是增加小样本早停探针，第三是引入内部的模拟预审与实验修复规划。

## 第 9 页：针对评审问题的改进一：事前验收协议

### 【页面视觉呈现】
- **`StructuredAcceptance` 事前验收协议设计**：
  - 在规划阶段签署形式化契约，实验前锁定预期目标，严防“事后根据数据挑指标写论文”；
- **契约核心约定字段**：
  1. `primary_metric`：明确主评估指标（如 Accuracy / MSE）；
  2. `metric_direction`：锁定优化方向为 minimize 或 maximize，不可中途篡改；
  3. `min_delta`：规定新方案相对于基线必须取得的最小提升幅度（例如 >= 0.05）；
  4. `oop_domination_margin`：池外基准压制容忍度，若新方法落后于常见的传统弱基线，直接裁定失败。

### 【逐字汇报讲稿】
> 针对“结论可能带有选择性报告”的问题，我们在规划模块引入了事前验收协议 `StructuredAcceptance`。
> 
> 它的核心逻辑是在跑实验之前，就通过代码把验收标准白纸黑字写死：锁定主指标是什么、是追求极大化还是极小化、相对基线必须提升多少个百分点才算有效。
> 
> 这样一来，如果实验跑出来的结果达不到预先签署的标准，系统就不能在正文里强行宣称取得了突破，从而在工程机制上杜绝了学术选择性汇报。

## 第 10 页：针对评审问题的改进二：小样本探针与早停剪枝机制

### 【页面视觉呈现】
- **PilotGate 小样本早停机制**：
  - 正式跑满全量实验前，先抽取 10%~20% 样本作为探针；
  - 引入现成的简单弱模型（如 `HistGradientBoosting`）作为“试金石”。
- **实测案例（特征缺失实验）数据**：
  - 候选方案在探针阶段 MSE: `0.3901`
  - 池外简单基线 (HistGradientBoosting) MSE: `0.0498`
  - 差距达到 `0.3402`，明显落后于传统方法；
  - **触发主动早停（status: pruned）**：
    - 盲目跑完全部实验需消耗：100,000+ Token
    - 早停提前退出仅消耗：**8,531 Token**
    - **直接节约 91.5% 的无效算力与 API 消耗！**

### 【逐字汇报讲稿】
> 针对“容易盲目空耗算力”的问题，我们设计了 `PilotGate` 小样本早停机制，这在我们的特征缺失实验中发挥了重要作用。
> 
> 在正式执行几十上百次调用前，系统先取 10% 到 20% 的样本跑一次预检探针，并拿一个未调优的传统模型（比如梯度提升树）作为对照。
> 
> 在实际测试中，探针检测到候选算法的均方误差为 0.39，而传统现成模型就能做到 0.04，候选算法明显落后。系统立刻触发早停，终止后续实验，将状态标记为 `pruned`。
> 这次早停让我们仅用了 8,531 个 Token 就及时止损，避免了跑满全量所需的 10 万多个 Token，真正实现了超过 91% 的算力节约，这切实验证了赛题对“资源消耗控制”的要求。

## 第 11 页：针对评审问题的改进三：内部模拟预审与实验大修规划尝试

### 【页面视觉呈现】
- **内部双层模拟评审机制（在送审前自我检查）**：
  - **Cold Review（事实检查）**：扫描正文中的数字与实验日志的一致性，防止大模型在写作时抄错数据；
  - **ConferenceReviewPanel（模拟评分）**：参照外部审稿网站的 4 维标准（Soundness 完备性, Novelty 创新性, Significance 实用性, Empirical 充分性）进行内部预审打分，设置 5.0 硬底线；
- **DeepRevisionManager（大修规划原型）**：
  - 解析审稿意见中提到的 Weaknesses，尝试自动生成补跑消融实验或追加对比基线的维修计划。

### 【逐字汇报讲稿】
> 此外，为了在提交给外部评审前尽量发现问题，我们在工作流里补充了一套内部模拟评审。
> 
> 第一层是冷审查（Cold Review），用脚本逐行核对论文正文里的数据和我们底层的实验日志是否一致，防止大模型写正文时产生文字幻觉；
> 第二层是内部评审面板，参考外部评审网站的 4 个维度进行打分预警；同时编写了 `DeepRevisionManager`，尝试把评审专家提到的“缺乏消融”等意见转化为后续的实验规划。
> 
> 虽然目前受限于算力和时间，我们还没有实现完全自动化的多次循环大修，但整个状态机的接口和规划链路已经跑通并纳入了测试。
